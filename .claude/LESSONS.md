# LESSONS.md — このプロジェクトで得た教訓

## 2026-10-02 lastIndexOf の「見つからない（-1）」に足し算をして、存在しない切れ目で分割した

- 症状: スレッド分割（`splitText`）で、絵文字だけの文章がサロゲートペアの途中（1文字目の半分）で切られた。
- 根本原因: 切れ目の候補を `lastIndexOf('\n\n') + 2` で計算していたため、見つからないとき（-1）に位置 1 を「切れ目あり」と誤認した（証拠: `splitText('😀'.repeat(10), 3, 3)` の結果が `["\ud83d", "\ude00", …]` になり、`-1` を 0 として扱う修正で解消）。
- 教訓: `indexOf` 系の戻り値に足し算・引き算をする前に、-1 を別扱いにする。分割・切り出し系の関数は「つなぐと元に戻る」不変条件のテストを、絵文字・空文字・区切りだけの入力で回す。

## 2026-10-02 Jev を使う設定でも Gemini の分類結果を一度代入していた

- 症状: Jev を使う設定で Jev が失敗したとき、種別が空になるはずが、Gemini が勝手に返した種別が残っていた。
- 根本原因: Gemini の結果を無条件に `result.kind` などへ代入してから、Jev の結果で上書きする順序だった。Jev が失敗すると上書きされず、スキーマで求めていない Gemini の値が残った（証拠: テスト「Jev が失敗しても全体は失敗にせず、警告を返す」で expected '' / actual 'schedule'）。
- 教訓: 「どちらの結果を使うか」を設定で切り替える処理は、上書き方式ではなく分岐（if / else）で書く。スタブは「仕様上返さないはずの値」も返すようにして、混入を検出できるようにする。

## 2026-10-03 設定を localStorage に直接書いて読み込み直さずに確認し、表示崩れと誤読しかけた

- 症状: 開発サーバーでの手動確認で、トーク本体から出典行と「詳細はスレッドで」が消え、日時の欄も隠れていた。
- 根本原因: 設定（GAS の URL と合言葉）を `localStorage` に直接書き込んだだけで、ページを読み込み直していなかったため、起動時の bootstrap（ひな形・種別の一覧）が読み込まれていなかった（証拠: 種別のラジオボタンが0個。読み込み直したら3個になり、出典行も出た）。
- 教訓: 手動確認で `localStorage` などの起動時に読む値を書き換えたら、必ず読み込み直してから観測する。おかしな結果が出たら、まず「前提の状態（設定・キャッシュ・サーバーのプロセス）が想定どおりか」を確かめる。偽の外部サービス（偽 Gemini）の応答の癖（30文字で切る等）による見かけの不具合も、実装の不具合と分けて裁定する。

## 2026-10-03 結果画面を「入力欄が先・コピーが後」で作り、実機で「どこをどう使えばよいかわからない」と言われた

- 症状: 初版の結果画面は、タイトル・概略・種別・日時などの編集欄を上に並べ、実際にコピーする「トーク本体」「スレッド」を画面の下に置いていた。ユーザーが実機で使ったところ、画面構成がややこしく、トーク本体のタイトルに【】が付いていることにも気づけなかった。
- 根本原因: 画面を「データの項目順（入力→出力）」で設計し、「利用者がやる作業の順（コピー→貼る→必要なら直す）」で設計していなかった（証拠: 「①トークに貼る→②スレッドに貼る→③保存」の順に並べ替え、編集欄を折りたたんだ版で、同じ使い方の質問が解消した）。最初の確認で画面一覧は提示したが、各画面の中の並び順と主な操作は提示していなかった。
- 教訓: 画面を提示するときは、画面の名前だけでなく「その画面でいちばん多くする操作」と「上から下への並び順」まで示して確認を取る。主な操作（ここではコピー）は画面の最初に置き、たまにしか使わない編集欄は折りたたむ。

## 2026-10-03 LLM の出力形式を指示文だけに任せ、長文の概略と、未確定の日付の言い切りが出た

- 症状: 「概略は4〜6行」と指示したのに、改行のない1段落の長文が返った。原文が「10月7日または10月8日のいずれか」なのに、トーク本体に「📅 10/7(水) 21:30〜22:30」と確定した日時が出た。
- 根本原因: 形式（行数・箇条書き）と不確かさ（日付が未確定か）を、プロンプトの文章だけで求め、コード側の整形・検証を置いていなかった（証拠: 実機の Gemini の出力で再現。スキーマに `dateUncertain` を足し、コード側で箇条書きへの整形・未確定時の日時クリア・原文の「または」「未定」の検出を入れて解消）。
- 教訓: LLM に頼む項目は、(1) 形式はコードで正規化できる形にして必ず整形する、(2) 不確かさ（未確定・複数候補）は専用のフィールドで返させ、コード側でも原文から機械的に確かめる。曜日と同じく「事実を言い切る出力」は、LLM の判断だけで決めない。

## 2026-10-03 ユーザーの「マージしました」を確かめずに次の作業へ進みかけた

- 症状: ユーザーから「マージして GAS を更新した」と報告を受け、main から新しいブランチを切った。直後の確認で、PR #2 はまだ OPEN で、main には変更が入っていなかった。
- 根本原因: ユーザー環境の状態についての報告を、観測（`gh pr view`）より先に事実として扱い、ブランチを切った（証拠: `gh pr view 2 --json state` が OPEN、`git log origin/main` が PR #1 のマージのまま）。被害は、空のブランチを1つ作っただけで済んだ。
- 教訓: 「マージした」「デプロイした」などの報告を受けたら、作業の前に `gh pr view --json state` や公開先の状態で確かめる。食い違いがあれば、責めずに事実だけを伝え、どちらに積むか（開いている PR に足すか、新しいブランチか）を決める。2026-07-12 の「ユーザー環境の状態を推測で断定」と同じ型。

## 2026-10-03 シェル経由の一括置換で、エスケープや改行が壊れて何度もやり直した

- 症状: Python のヒアドキュメントで `\r?\n` を含む正規表現を書いたら、実際の改行に変わって GAS のコードが壊れた。`node -e` の文字列や、バッククォートを含む bash のヒアドキュメントも、引用符・エスケープの解釈で失敗した。
- 根本原因: 複数行のコードをシェルの引用符の中に埋め込み、シェル・Python・JavaScript の3段階のエスケープ解釈を通していた（証拠: 書き込まれた `split(/?\n/)` の行。スクリプトをファイルに書き出して実行する方式に切り替えたら、一度で成功した）。
- 教訓: 正規表現・バッククォート・改行を含むコードを書き換えるときは、シェルの引用符に埋め込まない。Edit ツールで1か所ずつ直すか、書き換えスクリプトを作業用フォルダにファイルとして書き出して `node <ファイル>` で実行する。書き換えた後は `node --check` と `npm test` で必ず確かめる。

## 2026-10-03 Jev が 401 → 403 になり、原因（タグ0件か、キーか）の切り分けに時間がかかった

- 症状: 実機で「Jev による分類に失敗しました … Please check your API key」の警告が出た。ユーザーは「タグを1件も登録していないからでは」と考えていた。
- 根本原因: API キーの問題。タグ0件は無関係だった（証拠: 診断関数 `testJev` のログで、送った質問は kind と category の2つだけ、応答は HTTP 401 authentication_error。キーの頭の `apikey-` を削って貼っていたので付け直したら HTTP 403 に変わり、TypeSafe の管理画面でキーを作り直したら HTTP 200 で正しく判定された）。最初のキーが 401・403 になった細かい原因（`apikey-` の削除か、キー自体か）は、寄与は未確認。
- 教訓: 外部 API のエラーは、推測で原因を探す前に「何を送り、何の HTTP 番号が返ったか」を見られる診断関数を先に用意する（今回は `testJev` を追加してから一気に進んだ）。API キーは「表示された文字列全体」を貼るよう README に明記する。Jev のような任意機能は、失敗しても本体（Gemini）の判定で動き続けるように作る。

## 2026-10-04 「区切りから区切りまで」の置き換えで、間にあった関数まで消した

- 症状: シートの読み書きを見出しの名前方式に書き換えたところ、入力の検証のように列と関係ないテストまで17件失敗した（`validatePostInput_ is not defined`）。
- 根本原因: 書き換えスクリプトで「`/** 保存先シートを返す。` から `/** 保存内容を、シートの1行… */` の手前まで」を置き換えたが、その間に `sanitizeCellText_`・`validatePostInput_`・`normalizeTagsInput_` もあり、一緒に消えた（証拠: 変更前後の `^function` 一覧の比較で、意図しない3関数の欠落を確認。git の元のファイルから戻したら、残りは列の位置に頼ったテストの期待値だけになった）。
- 教訓: 区切りの間を丸ごと置き換える書き換えをしたら、直後に「変更前後の関数一覧の差分」を機械的に確かめ、消えた関数が意図したものだけかを見る。置き換える範囲は、関数1つずつ（開始の宣言から対応する閉じ括弧まで）に絞る。

## 2026-10-04 Windows のシェルから curl で日本語を送り、「カテゴリを選んでください」と誤ったエラーを見た

- 症状: 開発サーバーの確認で、正しいカテゴリ「お知らせ」を送ったのに「カテゴリを選んでください」と返った。
- 根本原因: Git Bash の `curl --data '…日本語…'` で送った本文の文字コードが崩れ、カテゴリ名が一致しなかったと見られる（証拠: 同じ内容を Node の `fetch` で送るスクリプトに変えたら、保存・検索・更新・削除がすべて成功した。curl 側の崩れ方そのものは確かめていないので、寄与は未確認）。
- 教訓: 日本語を含む API の手動確認は、シェルの引数ではなく、スクリプトファイル（Node の `fetch`）から送る。観測で「ありえないエラー」が出たら、実装を疑う前に送信手段を変えて再現するかを確かめる。

## 2026-10-05 教訓を書いた直後に、またシェルの引用符の中にコードを書いて失敗した

- 症状: テストを直すとき、正規表現と引用符を含むコードを `node -e "…"` の中に書き、構文エラーで失敗した（2026-10-03 に「シェルの引用符に埋め込まない」と記録した直後）。

## 2026-10-05 置き換え対象の文字列が2か所にあり、書き換えスクリプトが止まった

- 症状: 見出しの並び（`'出演者', 'メモ', 'ID'`）を置き換えようとしたら「見つからない」で止まった。実際は、同じ並びが別のテストにもあり、2か所で一致していた。
- 根本原因: 置き換え対象が1か所だけかを、書く前に確かめていなかった（証拠: `indexOf` で数えたら 2 件。前後の `]);` まで含めて範囲を絞ったら通った）。書き換えスクリプトの「ちょうど1か所でなければ止める」安全装置は、意図どおりに働いた。
- 教訓: 置き換え対象は、前後の特徴的な行まで含めて一意にする。止まったら、まず一致した件数と場所を表示して、どちらを直すべきかを判断する（もう一方は意図して残すこともある）。

## 2026-10-05 テスト用のスタブが本物の機能を一部しか真似ておらず、実装の不具合と見誤りかけた

- 症状: (1) 今月の使用量の集計のテストで、月が「2026-10-02 10:00:01」になった。(2) 公開用シートのテストで、タイトルの値が `=HYPERLINK(...)` の数式のままになった。
- 根本原因: どちらも実装ではなくスタブの問題だった。(1) 日付の整形のスタブが `yyyy-MM` の形に対応していなかった（本物の `Utilities.formatDate` は対応する）。(2) シートのスタブは数式を計算しないため、本物なら表示されるタイトルの文字ではなく数式が返った（証拠: スタブに `yyyy-MM` を足す・テストで数式から表示の文字を取り出す、の修正だけで通り、実装は変えていない）。
- 教訓: 新しい種類の GAS の呼び出し（新しい日付の形、数式、別ファイルの操作など）を使ったら、テスト用のスタブがそれを本物どおりに扱えるかを先に確かめる。テストが落ちたら、実装を直す前に「本物ならどう返るか」とスタブの返す値を比べる。

## 2026-10-07 絵文字の名前の判定を「コロンで挟まれた文字」で書き、時刻から文まで消すところだった

- 症状: Slack の絵文字の名前（`:mega:` など）を取り除く処理の初版で、「21:20よりスタート致しますので、よろしくお願い致します:mega:」が「21mega:」になった。名前が長い `:hand_with_index_finger_and_thumb_crossed:` は消えず、`:+1:` も残った。
- 根本原因: 「コロンで挟まれた、空白を含まない文字」という広すぎる決まりで書いた。時刻のコロンと絵文字のコロンの間の文全体を、名前とみなした。長さの上限（30文字）と「英字・かなを含む」という条件は、実在の名前（41文字、`+1`）を確かめずに決めた（証拠: ユーザーから届いた実際の Slack の文を、テストより先に試しのスクリプトで通したら3つとも見つかった。「数字で始まらない・句読点やかっこを含まない・60文字以内・`+1` `-1` は例外」に直して解消）。
- 教訓: 文中から記号の組を取り除く処理は、テストを書く前に、利用者の実際の文（PC 版・スマホ版の両方）で試し、変わった行をすべて目で見る。取り除く側の決まりは「何を残すべきか」（時刻・URL・ふつうのコロン）のテストも必ず一緒に書く。
